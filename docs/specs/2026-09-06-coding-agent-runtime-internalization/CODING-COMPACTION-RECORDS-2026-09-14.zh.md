# Coding 压缩的记录边界和私有数据隔离（slice83）

2026-09-14，rf/agent-capability-platform-v2 本地工作树。
Coding host2-coding-loop83；Nomi 保持 host53。未运行验证、服务、模型、迁移、commit 或 push。

## 已定位问题

原摘要输入把完整消息数组序列化后按固定 UTF-8 字节数切开，普通小消息也可能在字段
中间被拆开。摘要模型只能从“可能切开 JSON”猜测上下文。另一个具体遗漏是：
media_context 已删除独立 reasoning/signature 块和 Provider round ID，但仍把工具调用
provider_metadata 中的私有签名/续接数据发给摘要模型，尽管它们不是任务事实。

## 源码实现

- 新 compaction_source.rs 保存逐消息 JSON Lines 数据及原始消息索引/角色/边界；
  每条消息先经既有媒体、指令正文和 reasoning 清理，再序列化。清理只修改副本。
- 工具调用的 provider_metadata 仅在摘要副本中移除；原始调用参数、工具结果、
  durable journal、活跃模型历史和最新原文交换保留逻辑不被重写。
- 分片优先在窗口内最后一个完整消息边界结束，保持连续顺序，不跳过/重复任何
  已清理的源字节。超大消息仍在 UTF-8 边界拆分；每片带源字节范围、首尾消息索引、
  首条角色、是否从消息中间开始/结束，提示模型不要把片段当成完整工具结果。
- 在第一笔摘要模型请求之前算出整套分片。若完整记录优先打包超出剩余次数，
  切回带同样元数据的紧密 UTF-8 分片；不为漂亮边界降低原有紧密分片容量。
  两种方案都不能在现有每 turn 至多 32 次摘要请求内覆盖源时才拒绝。
  边界优先可能比紧密分片使用更多请求，但不提高总次数或每次字节/输出上限。
- 摘要源累计最多 64 MiB，在每条消息序列化/追加前计数拒绝越界；仅逐消息复制
  并清理，不先复制所有消息的媒体/私有块。原 HTTP/上下文/工具结果预算仍独立有效。
- run_compaction 的文本摘要先检查下一长度，再追加；终态必须 Completed 且摘要非空。
  原上下文只在全部摘要成功、最终替换满足完整 token/byte/message-count 预算并且
  ContextCompacted 记录成功后替换。失败不丢原历史、不自动重放工具。

## Codex 参考与区别

历史项移除以保留最近消息。借鉴的是历史项/近期上下文边界，而非照搬其丢弃或重试策略。
NomiFun 保留既有完整源的逐片摘要、mandatory accepted inputs、最新工具交换及原子替换；
本轮 JSON Lines 分片器为本地实现，不声称 Codex 使用相同算法。

## 未验证边界

消息边界不等于完整工具批次边界；跨消息的 call/result 仍可能在不同摘要请求中，
近期原文交换由已有 context_tail 独立保留。大消息/紧密回退仍可能切开 JSON 转义和字段，
片段元数据及提示只是解释约束，不是模型语义正确性的证明。
未运行 Unicode/转义、边界恰好相等、超大消息、32 次耗尽、取消、摘要超限、
敏感元数据隔离或真实长任务回归。也没有测量内存、费用或质量变化。
Engine 注册/Agent 选择/Session owner/权限和外部恢复边界不变，整体 CAR 不标完成。
