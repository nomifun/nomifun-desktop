# Coding 逐项工具结果记录（切片 64，未验证）

## 修正的问题

原串行执行分支把所有结果暂存在批次 Vec 中，最后统一调用 `finish_tool_results`。
这使前面已返回的结果可能因为后续调用取消、指令读取失败或事件写入失败而没有进入
Coding 语义日志。更重要的是，非 search 工具结果的身份/内容校验原先发生在批次末尾，
错配结果可能先清除 Patch 恢复义务或让下一个串行效果继续执行。

这不等于平台完全没有效果凭据：owner 的派发/结算仍独立持久化。但 Coding 的历史
重建和新加入的持久化工具档案只能读取已经记录的结果，不能从效果凭据猜造正文。

## 当前实现

- 每个真实串行调用返回后，先 `validate_for(expected_call_id)`，再执行 search 的
  路径指令后处理；非 search 结果也必须先核对，不再等到批次末尾。
- 统一 `record_tool_result` 规范化错误、再次校验投影后的结果，逐项发出
  `ToolCompleted`。只有事件 sink 成功返回后才进入下一个串行调用。
- Patch 成功必须在合法的成功结果记录后才清除恢复义务并持久化清除事件。记录失败
  则停止批次，之前 write-ahead 的恢复义务继续保留，不把日志失败当作回滚。
- 规划/steering/先前失败造成的串行暂缓结果也逐项记录，仍标为未派发，不增加效果
  或完成证明。正常返回的批次不再在末尾重复发出 `ToolCompleted`。
- 并行只读调用仍采用现有整批等待与固定结果顺序；每个结果先核对、完成指令后处理
  再记录，后续投影失败不吞掉已经成功记录的前缀。本切片没有把它改成乱序流式派发。
- 后续取消/失败不改变已持久记录的前缀。没有收到结果或记录不确定的调用仍保持未知；
  整体驱动 future 被丢弃、存储错误和进程崩溃仍按平台的持久化/清理合同处理，不能
  声称任何取消时刻都能保存所有尚在内存中的结果。

模型续轮仍要求整个批次完整。中断历史使用已记录结果和未知占位，真实结果不重放；
完成观察和 work_status 仍只在整批正常返回后更新。部分工具结果不是任务成功、
owner cleanup、进程退出或安全自动重试证明。没有引入第二套日志或效果管理器。
