# Coding：来源关联需求账本与完成覆盖（未验证）

任务 CAR-06 / CAR-07。在 `rf/agent-capability-platform-v2` 本地实施，未 commit/push。
按用户要求没有运行构建、测试、评测或 Provider 调用；只做源码阅读与局部格式化。
Coding build：`host2-coding-loop22`；Nomi 保持 `host9`。

## 具体缺口

此前 report_completion 只核对最新计划步骤。模型可以重写计划，移除某项工作，再提交
覆盖“剩余计划”的报告。观察调用 ID 与 workspace epoch 即使正确，也不能发现被删的义务。
本轮继续阅读本地 Codex 的 `core/src/tools/handlers/plan.rs`：其 plan tool 主要发布进度
事件，不把计划本身当作执行证明。本实现沿用这个边界，在 Coding 增加独立于步骤变化的
需求来源/覆盖约束，而不是声称从 Codex 移植了一个自动语义验收器。

## 模型控制接口

update_plan 接受可选 requirements 数组，新增条目包括：

- id：稳定 ASCII 标识，只允许字母/数字/-/_，最多 64 bytes；
- description：模型解释的义务或限制，最多 512 UTF-8 bytes；
- source：input 为零起始当前回合已接受输入索引，quote 为其中某个文本块的精确子串，
  最多 512 bytes。输入 0 是原始请求，后续是平台已接收的 steering。

首次建计划必须登记需求；后续可省略 requirements，保留已有账本。传入已有 ID 时，
描述与来源必须完全一致；只允许增加，不允许覆盖或删除。新输入至少要有一条来源关联记录，
但“一条来源”不等于已经完整提取该输入的所有子需求。任务包含多个义务时，模型仍应分别登记。
纯图片且没有非空文本的输入可用空 quote 表示来源身份，不宣称文本引用已验证图片语义。

账本限制 32 项/24KiB，update_plan 和 completion 参数各限制 48KiB；不能为绕过预算
偷偷丢掉旧需求。计划仍限制 16 步/64 次修改，必要时明确报告边界而非伪造完成。
PlanUpdated 先持久记录，再替换内存计划；已登记需求随原有计划上下文保留，不依赖聊天摘要。

report_completion 的每项 criterion 新增 requirement_ids（可为空，表示纯实施步骤），
整份报告必须将每个已登记需求恰好分配一次，同时仍覆盖每个当前计划步骤一次。
不知道的 ID、重复分配、遗漏、未登记新输入都会拒绝报告。supported 的观察证明规则不放松：
调用真实、成功、结算时可用且属于当前 workspace epoch；退出零不是测试/任务成功 oracle。

## 范围变化与披露

新增 scope_changed disposition，只允许在 criterion 指定 scope_change 引用时使用。
引用必须来自晚于所有受影响需求原始来源的已接受输入，必须有真实非空 quote，不能用
工具结果或同一条原始输入冒充后续范围变化，也不能将 evidence_call_ids 当用户授权。
旧需求仍保留，后续输入本身也须登记；不通过删除旧 ID 处理用户更正。

最终输出自动补充 unverified 和 scope_changed 项，列出原义务描述、理由及范围变化引用。
scope_changed 不被包装成原工作已完成。blocked 仍不能发布正常任务完成，运行进程和
过期观察也仍会阻止完成。新输入、计划、工具观察均使旧完成报告失效。

这些引用仅证明“这段文字来自哪个已接受输入”，不独立证明它确实撤销了旧需求，也不判断
模型是否截取了否定句中的错误子串。语义解释仍须遵守完整 Agent/用户指令；该字段不授予
任何新操作权限。尤其不能因用户不允许验证，就用“完成证明需要证据”为由执行测试。

## 架构与未完成事项

这是 Coding Engine 自己的任务循环/上下文/完成策略，不在平台建立第二个任务数据库或
权限系统，不要求社区 Engine 复用 Coding 的计划工具。平台仍负责已接受输入、效果和清理。
来源只在 retained_inputs 查找，不能在历史计划、工具输出、内部 review 消息或摘要中查找。
当前回合不从历史计划自动恢复需求；跨回合持久任务续跑属于尚未完成的安全恢复设计。

新字段在持久事件解码时允许缺省，但当前报告准入必须有真实登记记录；历史报告不是当前证明。
构建摘要包含 requirements.rs，exact build 递增，不借用旧 build 的恢复假设。

仍未实现独立需求提取完整性、逐义务语义相关性或自动判定“用户确实撤销”的证明。仅检验
账本覆盖和来源关联不能解决这些问题。其他协议/生态资源、复杂路径指令、安全恢复、真实
provider/consumer/跨平台验收也未完成。本轮没有增加或执行测试；后续需要覆盖删步骤漏项、
伪造/历史/工具来源、重复 ID、预算、新补充输入、范围变更时序和最终披露，不引用旧测试背书。
