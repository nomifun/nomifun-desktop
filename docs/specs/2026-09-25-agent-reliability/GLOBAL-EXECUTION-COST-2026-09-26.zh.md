# 通用 Agent 执行开销的全局排查

## 结论

通用 preset 的职责包含开发工作。能力授权的广度、模型当前看见的工具描述数量、执行流程需要的控制强度，应当分开管理。本次慢会话主要暴露了上下文压缩和执行控制的成本问题。

本次调查和修复围绕真实会话 `01a0d946-4327-7033-b8ee-8e08faaa8434`，输入为「帮我写一个五子棋的H5游戏」。该会话最终产生了 completed 事件和一次成功文件写入，但从创建/受理到完成约 334 秒，即 5 分 34 秒。这里的 completed 是执行状态，不是独立游戏可玩性验收。

实际开发数据目录为 `%LOCALAPPDATA%/NomiFun-dev-schema-b40e0155e59ea087`。会话使用通用 preset revision 2、`step-3.7-flash`、OpenAI Chat 协议，运行时 build digest 为 `cb56f0c68d96a416acec5c8acb91e844dddb8f6369645d601b0850bd99d69c12`。调查只读原数据库和日志，保留原任务、文件及终态。

## 根因与设计层次

### 1. 压缩器进行了过多串行生成，且压完仍然接近触发线

旧实现把压缩源分片大小与输出预算绑定：4,096-token 输出预算最多对应约 6 KB 源片段。每段依次请求模型，用前一段摘要再摘要后一段。一个几十 KB 的普通工作上下文因此变成多次串行推理；摘要超限还会缩短重试和再拆分。

同时，旧流程先摘要整个历史，再把最近至多三个工具批次原样加回来。这些内容既被摘要又被保留，造成重复工作。它只要求压缩后低于同一触发线，没有给后续工具结果留出充足余量。第 1 次替换花 6 次生成仅减少约 2.9 KB，随后很快再次进入压缩，形成明显的开销放大。

### 2. 完整能力集合被直接当成了每轮工具描述集合

应用编译全部可用工具时，标准、平台和外部工具描述都默认 `deferred=false`。虽然已有冻结 ToolPlan 内的 ToolSearch 机制，大型通用工具表仍然在每次模型请求中完整呈现。

既有 D-023 已明确 [role-complete but context-minimal](../2026-08-28-agent-capability-platform-v2/DECISIONS.zh.md)：能力完整，低频/重型描述按需提供。执行权来自 Snapshot/Kernel；描述暂时未展开不应该改变权限，也不应该让模型误以为该能力不存在。

### 3. 当前可调用状态与展示给模型的工具没有同步

当前策略在第二个 workspace 工具批次就激活结构化计划和完成账户。失败效果还会置 `needs_replan`。但模型请求仍然展示写文件等当前必定会被门禁拒绝的工具。

本会话第 6 步生成了约 9.4 KB 的完整 HTML 参数，直到生成结束才因缺少有效计划被拒绝；模型建立计划后，第 8 步又生成了完整文件。形式控制既花了额外轮次，也造成整份代码的重复生成。

本次保留已有完成契约，修复“明知当前不能调用，仍邀请模型生成完整效果参数”的呈现问题。未将“工具成功”改成“功能已经验收”。

### 4. 工具输入约定与常见调用习惯存在摩擦

- 第 1 步把 `ls -la` 放入 `exec_command.command`。这个工具实际运行可执行文件加独立 args，并不解析 shell 命令行。当前平台是 Windows，错误直接进入了恢复路径。
- 第 2 步 `search_files(path=".", query="五子棋")` 被底层通用路径规范化拒绝；目录搜索应接受工作区根的常规写法 `.`。
- 第 10 步只更新计划状态，因省略 `explanation` 被拒绝，必须再调用一次。这类不改变任务范围的状态更新不需要强制重新描述原因。
- 完成报告把同一要求关联到两个步骤，触发已有的唯一归属检查，又增加了一次调用。本次保留此完成账户约束。

### 5. 历史执行预算必须与当前配置分开分析

该回合持久化的执行预算为 32,768 context tokens、4,096 output tokens、1,024 个主模型步骤。当前 provider 配置是 context_limit=200,000、compaction_threshold_pct=90、output_limit=null，但它的更新时刻为 **2026-09-26 00:02:41.959（上海时间）**，晚于该回合 **2026-09-25 23:59:49.895** 的完成时刻。

因此不能把当前 200K 配置当成慢回合已经采用的预算，也不能通过单纯调大某一个模型窗口来掩盖上述通用执行成本问题。本次没有修改用户的模型配置。

## 已落实的调整

```mermaid
flowchart LR
  S[冻结 Snapshot 的完整能力与资源] --> P[完整 ToolPlan]
  P --> V[首轮核心工具与按需目录]
  V --> G[按现有执行门禁呈现可调用工具]
  G --> M[模型推进任务]
  M --> K[Kernel 与真实领域 owner]
  K --> E[真实回执与当前验证观察]
  E --> C[当前上下文]
  C --> H[只摘要较早前缀并保留近期完整批次]
  H --> M
```

1. **按输入容量分片。** 压缩源按实际输入预算、滚动摘要和序列化余量规划，最大 48 KiB，不再把 4K 输出预算直接限制成 6 KB 输入。若 JSON 转义导致实际请求过大，在花费模型请求前按连续范围拆分；输出超限时的有界重试、降级说明和累计预算仍保留。
2. **先选择保留内容，再摘要剩余前缀。** 近期完整工具批次、已接受输入和必须保留的原图遵循原有约束。近期原样保留的内容不再送去重复摘要；可选近期内容的选择为有效触发预算留下约 20% 余量。
3. **按需呈现大型工具表。** 当初始 schema 大于 24 KiB 且存在已授权 ToolSearch 时，保留日常 workspace、Web、协作入口；其他 schema 留在完整 ToolPlan 中按需展开。模型看到由实际冻结工具生成的能力目录。小工具表或没有发现接口的会话继续完整呈现，不会把工具藏到不可用。
4. **呈现遵守当前门禁。** 需要恢复规划时及时暴露计划控制；已有计划门禁阻止效果调用时，临时隐藏对应效果描述，保留只读、规划和进程清理入口。Kernel 的执行检查、完整绑定和权限仍然存在；owner 的 Specific 选择保持原语义。
5. **降低无意义格式重试。** `search_files` 独立接受根目录 `.`，不放宽写入/删除的通用路径规范。`exec_command` 描述给出真实 host OS。只有在步骤、要求和恢复状态都未改变时，计划状态更新才可省略 explanation，并保留原说明；新计划、改范围或恢复仍要求说明。
6. **更新 build digest。** 新增的工具呈现模块纳入运行时源码摘要，避免不同执行实现被当成相同检查点版本。

## 验证结果

- `cargo test -p nomifun-agent-runtime -p nomifun-file --lib`：Runtime **115 通过**，File **231 通过**。
- `cargo test -p nomifun-app --test native_coding_reliability --features browser-use,computer-use -- --nocapture`：**3 通过**。
- `git diff --check`：通过。

上述 Rust 命令通过既有 Windows 工具链环境 wrapper 执行。没有运行全仓库测试或修改 renderer。

构造场景使用约 10 KB HTML 数据和与桌面一致的通用 Browser 资源绑定，覆盖实际 API → preset → provider 编码 → Runtime → Kernel → File owner → journal 链路：

| 首轮工具呈现 | 可见工具数 | schema 字节数 | 完整请求字节数 |
| --- | ---: | ---: | ---: |
| Coding preset | 25 | 22,110 | 25,725 |
| 通用 preset | 21 | 20,309 | 24,782 |

这是修改后同一构造夹具的比较，不是将不同真实任务的 token 账单直接相减。完整授权工具没有按这些数量裁剪。测试另外通过 ToolSearch 载入原有 `browser/navigate` schema，并确认绑定/发现阶段没有启动浏览器运行时。

三个应用场景分别使用 6、7、7 次构造主模型请求，每个场景只发生一次写入，均为 **0 次压缩**；额外轮次分别用于故意注入的协议错误和非开发工具发现。它们仍执行既有计划/完成账户，且明确标记游戏功能未独立验收。模拟 provider 的时间不代表真实模型延迟。

压缩专项测试另覆盖：约 43 KB 的较早历史在一次摘要请求中处理；近期完整文件参数不进入摘要源、仍留在后续上下文；压缩后减少超过 25% 原始上下文字节；追加较小观察不立刻再次压缩。已有输出截断、图像保留、恢复、工具身份、权限和计划完整性测试继续通过。

测试发现并修正了一处本轮回归：及时激活恢复控制最初误作用到失败协作调用，已限定为需要 workspace 账本的操作，原协作行为测试重新通过。应用夹具最初没有实际绑定 Browser 资源；补齐真实桌面资源条件后，非开发工具发现测试通过，相关初次失败日志保留。
