# 插件与小程序的 Agent 模块重构方案

日期：2026 年 10 月 2 日。性质：完整目标设计。实际实现、验证证据与剩余工作单独记录在 [实施记录](IMPLEMENTATION.md)，不以本文的目标描述作为已完成证明。本次整理只调整方案文档。

本方案把“插件与小程序”的创建、修改、验证和管理操作抽离成一个可选的 Agent 功能模块。用户点击创建时，系统检查默认 Agent 是否具备这个模块；已开启则进入普通会话，未开启则进入 Agent 工作台，配置完成后带着原需求继续。创建任务以经过验证、已安装且实际可使用的插件作为交付结果。

本次检测的是整个插件开发模块。每个生成出来的插件是该模块的成果，不需要在创建前选择或授权一个尚不存在的插件。本次也不建设“每个插件分别绑定哪些 Agent”的新配置系统。

方案采用以下核心决策：

1. 创建与修改统一进入普通会话，插件库保留成果管理和一个创建快捷按钮。
2. 新建任务使用配置的默认 Agent；已有会话使用当前 Agent。
3. 开始任务前检查整个插件开发模块与必要操作权限，缺少时进入工作台并保留原需求。
4. 模块接入现有 Agent 注册、工具调用、执行与恢复机制；插件运行继续使用统一 Plugin Core。
5. 一次需求经过实现、构建、真实验证、自动修复、安装和正式交付检查，才能判定完成。
6. 旧 Creator、整包一次性生成接口和独立生成 worker 在迁移后退出，已有插件与用户数据保留。
7. 本次不新增每个生成插件分别选择 Agent 的绑定系统，沿用现有扩展点消费规则。

## 1 功能模块与生成成果的边界

为避免“插件能力”一词同时指代不同事物，统一使用以下名称。

| 名称 | 含义 | 状态归属 |
| --- | --- | --- |
| 插件开发模块 | Agent 创建、编辑、构建、验证、安装与管理插件的功能，对外显示“插件与小程序” | 该 Agent 的功能配置与操作授权 |
| 已安装插件 | 一次创建或导入得到的实际应用包与本机实例 | 插件库、实例启停、配置及运行状态 |
| 插件扩展点 | 具体插件声明的 Agent 工具、上下文、拦截器、桌面命令等 | 现有 Action 与 Binding 机制 |
| Plugin Core | 管理包、安装、存储、运行和扩展点的宿主底座 | 应用装配与统一插件平台 |

以“文档摘要插件”为例：默认 Agent 先开启插件开发模块，才能执行创建任务；创建结果是一个摘要插件，它的摘要工具随后通过现有扩展点使用。创建模块的开关与摘要插件的启停开关分别控制不同对象。

本次采用以下范围：

- Agent 功能模块只有一个主开关，作用于整个插件开发功能。
- 开启该模块时，按用户选择授予完成创建所需的操作权限。
- 每个插件沿用插件库中的启停、配置和扩展点规则。
- 小程序由用户直接打开，运行不依赖创建它的 Agent。
- 单个插件面向哪些 Agent 生效，是独立的扩展消费策略；本次不新增逐插件选择 Agent 的页面、数据模型或前置步骤。
- 创建能力被关闭，不删除已有插件、配置和用户数据。

模块开关只控制 Agent 能否执行这些开发与管理操作。插件库的查看、打开、配置等人工操作仍由 Plugin Core 的既有权限控制，不随某个 Agent 的模块开关消失。例如，关闭开发模块后，用户仍可打开已经安装的待办小程序。

## 2 产品目标与重构范围

| 目标 | 本方案的具体行为 |
| --- | --- |
| 统一会话 | 创建、继续修改、修复都使用普通 Conversation 的消息、输入框、执行轨迹和历史 |
| 入口简洁 | 主入口在会话；插件库保留一个“创建”快捷按钮，统一转入同一会话启动流程 |
| 默认 Agent | 新建插件任务使用工作台配置的默认 Agent；已有会话中的任务继续使用当前 Agent |
| 先检测功能 | 检查整个插件开发模块、必要操作授权和真实运行依赖 |
| 未开启时引导 | 工作台定位对应 Agent 与模块，保留需求；用户开启并保存后继续 |
| 一键生成 | 一次提交由系统完成实现、验证、修复、安装和交付，需要真实配置或授权时可暂停续作 |
| 可用性 | 由真实运行和业务验收证明可用，模型回复或文件存在不作为成功证明 |
| 可插拔 | 模块通过现有 Agent 注册机制装配，可撤销贡献；Plugin Core 保持独立生命周期 |
| 破坏性重构 | 删除独立 Creator、单次整包 JSON 生成、平行聊天和生成 worker |
| 数据保护 | 保留已安装实例、有效草稿、用户数据、配置、授权及历史关联 |
| 支持目标 | 遵守 Tauri Desktop 与桌面级 WebUI 的 880×600 合同，保留现有 WebUI 只读边界 |

不新增插件专属 Agent 类型、插件专属会话分组、第二套模型执行器或第二套安装平台。可靠的包、存储和安装底座继续复用。

## 3 重构前的问题与失败基线

以下是此前源码检查记录的旧链路问题，作为重构基线。部分旧实现已在工作树中调整或删除，表格不是当前实现状态清单。真实用户失败任务尚未完整复现，不能将“从未成功”全部归因于其中某一个异常。

| 旧链路事实 | 影响 | 原源码依据 |
| --- | --- | --- |
| 多个入口导航到独立 Plugin Creator | 会话、插件库和工作台的创建路径分散 | PluginLibraryPage、PluginWorkspace、PluginRunPage、AgentContributionOrder |
| Creator 单独选择模型，不解析默认 Agent | 创建绕过 Agent 功能、操作授权和运行配置 | PluginCreatorPage 的 send |
| 后端要求一次返回完整 files JSON，输出预算为 16000 token | 包完整性、转义、格式或截断问题导致整轮失败，没有工具驱动的修复循环 | run_draft_generation、provider_config.rs |
| 需求与助手消息仅在包校验成功后加入 Draft messages | 失败需求缺少创作历史依据，难以诊断与继续 | run_draft_generation |
| 独立 worker、内存任务表、长 HTTP 等待和前端轮询 | 与会话事件及恢复机制分离，重启后生成状态被结算为失败 | generate_draft、recover_interrupted_draft_generations |
| 多类错误归入 PLUGIN_GENERATION_FAILED，前端展示通用文案 | 用户看不到实际失败阶段和解决动作 | PluginHttpError、PluginCreatorPage |
| inspect_files 通过即可成为 Ready | 结构合格不能证明业务功能可用 | run_draft_generation |
| UI 健康检查主要读取 UTF-8 HTML，Service 检查主要启动并停止 | 缺少真实 UI 交互、Action 结果与需求验收 | PluginServiceRuntime |
| 旧 preview 接口要求有 UI | 无 UI 能力插件缺少等价的创作试运行入口 | preview_draft |
| 成功生成测试用 wiremock 返回预制源码 | 能证明部分安装集成，不能证明真实模型从需求生成成功 | plugin_e2e.rs |

发布验收前应保存真实失败样本，包括原需求、选定 Agent 或模型、协议、错误阶段、错误码与脱敏日志。用相同需求对照验证新链路，区分入口和协议设计问题、模型连接问题、Runtime 问题与插件代码问题。不能以“重新设计了流程”代替失败原因定位。

## 4 入口与默认 Agent 的启动流程

### 统一入口

会话中的“创建插件”、插件库唯一的“创建”快捷按钮、已有插件的“继续修改”、工作台的扩展点模板创建，均调用同一启动协调服务。

插件库保留成果管理界面与实际运行页面。重复的侧栏和页面主创建按钮合并，不再进入独立创作页面。插件模板是创建意图的参数，不是另一个聊天入口。

~~~mermaid
flowchart TD
    A["点击创建插件"] --> B["读取配置的默认 Agent"]
    B --> C["检查整个插件开发模块"]
    C -->|已开启且操作权限完整| D["进入普通会话"]
    C -->|未开启或操作权限不足| E["Agent 工作台定位该模块"]
    E --> F["开启并保存继续"]
    F --> B
    D --> G["输入或继续原需求"]
    G --> H["生成、验证、修复、安装与交付"]
~~~

点击创建但尚未输入需求时，检测通过后进入现有 /guid 会话创建页面；不创建空插件、空 Draft 或后台生成任务。已有已提交需求时，复用普通会话创建和首消息发送，接受任务后才创建插件草稿。

### 检测对象与来源

新建任务使用 guid.defaultAgentSelection 所代表的工作台默认选择，并与普通新会话使用同一解析规则。最近一次选中的 Agent 或 nomi.defaultModel 不代替这个选择。

后端做权威检测，前端只负责展示与导航：

1. 默认 Agent 引用有效，有稳定可执行版本，或官方模板可编译为有效配置。
2. 该版本已直接开启插件开发模块。
3. 操作授权包含创建闭环所需的草稿读写、检查、试运行和安装；仅授权读取不算具备创建能力。
4. 模块已经注册，真实 handlers 与 Host Ports 可用。
5. Agent 的模型路由支持所需工具调用，使用其既有路由和故障转移规则。
6. 当前平台支持适用操作，并具有本阶段必需的运行依赖。

没有需求、尚未确定插件形态时，只检查通用必需条件。需求明确需要 Service 后才追加 JS Runtime 的要求，不因为缺少 Node 而阻止 UI-only 小程序。

| 情况 | 行为 |
| --- | --- |
| 模块与必要授权完整 | 直接进入普通会话 |
| 模块未开启 | 工作台打开对应 Agent 的功能页，定位“插件与小程序” |
| 已开启但只有读取权限 | 工作台明确缺少创建或安装操作，保存后继续 |
| 默认 Agent 不存在或未保存 | 工作台修复默认选择或稳定版本，不默默换 Agent |
| 模型或依赖不可用 | 给出具体问题和已有修复入口，保留创建意图 |
| 检测请求失败 | 在当前入口显示重试，不把未知状态当作未开启 |
| 当前 WebUI 不支持本机写操作 | 按现有只读规则显示不可用，不开放绕过接口 |

工作台往返保留需求、附件引用、目标插件版本和来源位置。URL 只携带不透明意图引用，完整内容保存在现有会话草稿机制中。

用户点击“开启并继续”后保存稳定配置，再重新检测。工作台必须提供一个完整的创建操作组合，包含读写、验证和安装，防止出现开关已开却无法创建的情况。管理与永久删除等操作分别授权。

官方默认 Agent 的模板不被直接修改。用户的功能变更保存为正常个人预设；“保存为默认并继续”明确说明会更新默认选择，不暗中创建专用插件 Agent。

没有已提交需求时返回输入框等待输入；此前已经提交时继续原请求。重复点击、刷新和返回采用同一意图与发送幂等键，只接受一次任务。实际启动时重新校验稳定版本，避免检查后配置改变。

### 已有会话与修改插件

已有会话中的创建或修改任务使用当前 Agent，保留上下文。缺少模块时引导配置该 Agent，通过既有 Agent 切换或接续规则在后续安全回合生效，不自动改用全局默认 Agent。

插件库的“继续修改”优先回到原创作会话；原会话不可用时，用默认 Agent 启动新的普通会话，携带插件引用与版本。打开已安装小程序、浏览插件库不检查创建模块。

## 5 可插拔模块的架构

建议提供官方功能包 nomifun.plugin-development，注册一个 Agent Module plugin.development。工作台显示“插件与小程序”，用户只需理解这个模块提供插件开发与管理操作。

~~~mermaid
flowchart LR
    A["Agent 功能配置与操作授权"] --> B["Compiler 与执行快照"]
    B --> C["普通会话 Runtime"]
    C --> D["插件开发模块工具"]
    D --> E["Plugin Development Service"]
    E --> F["统一 Plugin Core"]
    E --> G["受管构建与验证端口"]
    F --> H["Artifact 与插件数据"]
    F --> I["UI Surface 与 JS Service"]
~~~

| 构成 | 职责 |
| --- | --- |
| Module 合同 | 具体 Action、输入输出 schema、操作效果、资源需求与可用性 |
| 创作指引与模板 | 当前包格式、真实 SDK、模板及分步开发流程，帮助同一 Agent 正确使用工具 |
| 工具 handlers | 调用真实的草稿、构建、验证、安装和库管理服务 |
| Host Ports | 连接实际文件、构建工具、Surface、Service 和运行观察 |
| 工作台元数据 | 主开关、必要授权组合、依赖诊断 |
| 会话成果适配器 | 插件卡片、预览、文件和验证结果，复用通用 Workspace |

沿用现有 PluginRegistration、Catalog、Compiler 和服务装配机制，不在 Runtime 中增加插件专用模型循环。仅加入 Prompt 或 Skill 不算实现模块；实际调用必须经过 Agent 快照与操作授权。

Agent 模块是 NomiFun 提供的创作功能包，生成成果是标准 Plugin Package。两者无需使用同一种安装方式，Plugin Core 也不依赖 Agent 模块才能运行，避免创作功能依赖自己先创建一个插件的循环。

### 模块的操作合同

| 操作组 | 目标 Action 语义 | 约束 |
| --- | --- | --- |
| 查看 | 列出、读取插件与草稿 | 按 owner 过滤，不暴露秘密 |
| 草稿 | 创建或打开指定插件的工作副本 | 绑定来源会话与目标插件版本 |
| 文件 | 读取、原子应用补丁、替换与删除 | 限定受管草稿与预期 revision |
| 检查 | 冻结源码、构建产物、返回结构化诊断 | Host 执行，模型不能自报通过 |
| 试运行 | 打开、观察、调用与关闭 UI 或 headless Preview | 临时数据，真实 SDK 与 Runtime |
| 安装 | 保存新插件或更新指定版本 | 精确验证回执、配置、授权与 CAS |
| 交付检查 | 读取已安装版本，检查正式入口及实际 Action | 使用真实消费路径，遵守外部效果授权 |
| 管理 | 配置、启停、导出、回收、恢复、删除 | 具体 Action 分别授权，创建权限不包含删除其他插件 |
| 清理 | 丢弃草稿与释放临时预览 | 不删除已安装成果与生产数据 |

对外保持一个主功能开关。默认创建操作组合覆盖读写草稿、检查、试运行、安装和交付检查；管理操作可在详情中单独授权。系统从现有 Module 和 Action allowlist 计算状态，不新增另一套能力开关事实。

工具请求使用结构化输入，返回真实结果与稳定诊断。涉及修改时携带预期 revision，涉及重试时携带操作幂等依据。同一个幂等键对应不同参数应拒绝，不能静默复用旧结果。Host 检查 owner、来源会话、版本和适用权限，模型不能填写验证通过标记或替用户确认授权。

不要求默认通用 Agent 获得完整 Shell、VCS 或任意文件系统权限。常规创作使用受管草稿工具，构建由 Host 在确定的工作目录执行。

### 插拔与关闭的语义

- 功能包未装配时，模块显示不可用，保留已有配置与诊断。
- Agent 未开启时，不向其物化本模块的工具与创作上下文。
- Agent 配置关闭模块后，后续任务启动不得获得该模块；已有快照不会被原地改写，在途任务沿既有规则完成或由用户停止。
- 撤销功能包的注册时，撤销其调用准入，结算或取消在途操作，清理临时资源，保留有效草稿。
- 已安装插件的 UI、Service、数据与管理界面继续由 Plugin Core 承担。
- 停用一个实际插件通过其既有生命周期控制，不能用关闭创作模块代替。

## 6 首期支持的生成范围

首期支持统一包格式的三种形态，使用同一创建流程：

| 形态 | 组成 | 验证和使用 |
| --- | --- | --- |
| 小程序 | UI，可使用插件本地存储 | 验证真实交互与持久化，保存后直接打开 |
| 能力插件 | Service 与已注册 Binding，可以无 UI | 验证实际 Action 及扩展点消费，按现有规则启用 |
| 混合插件 | UI、Service 与可选 Binding | 验证 UI 到 Service 的调用和共享持久数据 |

优先支持自包含 HTML、CSS、JS 与 Service ESM，使用标准 Manifest、SDK 和已实现的 Host API。自由需求可在该范围内实现，模板提供可靠起点，不把产品限制为填写模板。

依赖外部服务的需求需要真实可用的 API、配置和 Credential 引用。缺少时显示等待输入，保留工作成果；无法支持的原生能力、外部依赖或扩展点给出明确诊断，不生成占位 API 或假实现。

如采用 React 等作者源码，构建工具由 Host 受管并固定版本，最终产物仍是自包含统一包。运行插件不要求用户执行 npm install、启动开发服务器或依赖 CDN。

首期不建设插件市场、发布平台、逐插件 Agent 分配系统或不可信代码沙箱产品。这些均不属于当前需求的完成条件。

## 7 从需求到可用插件的完整流程

~~~mermaid
flowchart TD
    A["需求持久化"] --> B["明确功能与验收条件"]
    B --> C["打开受管草稿"]
    C --> D["Agent 分步实现"]
    D --> E["检查与构建"]
    E -->|失败| R["同一 Agent 修复"]
    E -->|通过| F["真实试运行与业务验证"]
    F -->|失败| R
    R --> D
    F -->|通过| G["统一安装或更新"]
    G --> H["已安装入口与成果检查"]
    H -->|可修复失败| R
    H -->|通过| I["持久化交付回执并报告成功"]
~~~

1. **接受需求。** 使用普通会话首消息或后续消息的持久化与幂等机制，先保存原需求、附件与交付类型。失败请求也必须能在会话中定位。
2. **明确需求。** 同一 Agent 提取必需功能、数据、UI、外部依赖与可执行验收条件。只为会影响实现的缺失信息询问，不要求每个简单任务先填写需求表或逐步批准。
3. **打开草稿。** Host 按当前 schema 创建标准 Manifest 与适用模板；修改已有插件时记录 plugin_id 与基线 revision。
4. **分步实现。** Agent 通过工具逐步读取与修改文件，每次变更可追踪并保持原子性；删除文件有明确语义，取消保留最后一个一致版本。
5. **检查与构建。** Host 验证结构、语法、依赖、SDK 和运行入口，产生不可变 Artifact 与结构化诊断。
6. **真实试运行。** 打开受管 UI Surface 或 headless 验证入口，观察实际运行并执行与需求对应的用例。
7. **自动修复。** 失败项反馈给同一 Agent，按原需求修正后重新构建与验收，有预算和次数上限。
8. **安装或更新。** 复用统一 Install Service 的 Stage、Validate、CAS、数据处理和 Activate；不能以验证预览替代安装。
9. **检查交付。** 确认安装版本与测试版本一致，插件库可读取，正式入口可打开或调用。
10. **结算成功。** 持久化明确的 Plugin 成果回执，显示打开、试用、继续修改或必要配置入口。

不再要求模型一次回复完整包的 JSON。标准字段由 Host 初始化，SDK 指引从当前实际合同校验，构建与调用使用真实工具。例如 desktop.files.open 当前生产 owner 明确不可用，Agent 不能仅凭接口名字宣称它已实现。

### 回合结束与任务成功

模型回合结束、构建通过、安装提交、整个创作任务成功需要分别表示。安装提交后仍处于交付检查阶段；只有所有必需交付条件通过才能报告成功。

普通会话的请求记录应包含类型明确的插件交付要求，关联原需求、目标成果与草稿。Runtime 在结算前检查 Host 的交付事实：没有生成成果、验证未完成或安装尚未确认时，将任务保留为未完成、等待输入或失败，不接受模型文本作为成功依据。这是现有会话执行合同的扩展，不另建插件任务调度器。

同一请求要求多个插件时，分别记录每个必需成果，全部满足对应交付条件后才结算整个请求。仅有一个旧 plugin_id、部分成果成功或此前版本验证通过，不能证明本次新建或修改任务已完成。需求变更通过新的会话请求更新验收版本，不能在失败后悄悄删除原必需功能。

生成能力插件不强制用户再选择使用它的 Agent。基础交付验证其已安装、按声明启用且正式消费入口可调用，沿用现有扩展点生效范围。

如果需求明确要求当前会话立即使用新工具，则额外验证该会话的真实调用能力。当前工具索引可能需要在安全回合边界重建，必须遵守既有 Agent 切换、在途效果和活动 AgentExecution 限制，不能假设安装后任意会话都会自动热加工具。模型回合结束但创作请求尚在交付阶段时，不得先报成功再补验证。

不满足安全接续条件时应明确显示当前会话接入待完成，而不能把 Action 已注册当作目标会话已能调用。该要求只适用于明确包含此目标的需求，不扩大为所有插件创建的前置条件，也不引入新的逐插件 Agent 配置平台。

## 8 可用性验证与成功条件

| 验证层级 | 必须证明的事实 |
| --- | --- |
| 包与构建 | Manifest 合同、文件路径、入口、源码语法、实际依赖、SDK 和 Host API 兼容 |
| Runtime | UI 真正加载并完成 Bridge 握手；Service 能 activate、执行适用 Action 并按合同响应 |
| 业务 | 明确需求对应的真实交互或调用产生正确结果，输入输出 schema 与 Binding 合同符合要求 |
| 数据 | 使用真实插件存储，重建 Surface 或 Service 后保留数据，迁移保持适用数据 |
| 交付 | 已安装版本与验证版本相同，正式打开或调用入口可用，成果回执持久化 |

例如持久待办小程序至少执行“添加待办、完成待办、关闭再打开、确认数据保留”。能力插件需要验证指定输入和业务输出，以及实际声明的扩展点消费路径；不能用 Desktop 命令证明一个只声明 Agent Tool 的插件已经可用。

生成时在受管验证环境重建 Surface 或 Service，不重启用户正在工作的整个 NomiFun。产品发布验收再覆盖应用完整退出和启动后的数据恢复。

### 验证证据与版本

验证由本模块的应用服务调用现有构建、Surface、Runtime 与存储端口执行，不另建测试环境产品或独立任务调度器。UI 验证使用实际产品 Surface；仅加载一个相似网页不能证明真实 SDK 和权限行为。

需求中的必需项在实现前固化；Agent 可补充测试，但不能删除必需项、降低预期或用自报 passed 文本作为证据。模板有 Host 维护的基础用例，自定义需求记录实际执行的步骤和观察结果。有限测试只证明已检查的条件，界面审美等主观结果通过预览反馈继续修改。

每个必需功能需要关联至少一个适用的验收条件；持久化需求必须包含重建运行环境后的读取检查。用例的步骤与预期在执行前持久化，即使超时、取消或页面断线，该用例仍是待验证或失败。不得只保留成功用例，或把实现实际输出反过来当成需求的正确预期。

Host 生成的验证回执至少关联 owner、来源会话与消息、需求摘要、draft revision、artifact_digest、配置和权限摘要、Credential 引用版本、Host API、验证工具版本与逐项证据。凭据明文不得进入报告。

修改代码、需求、配置或执行授权后，旧回执不证明新版本已通过。install 检查精确 Artifact 和验证上下文，不能沿用其他版本的成功记录。

安装前检查在临时环境完成业务用例；安装后检查通过正式入口确认相同版本的 UI 或 Action 实际可达，并进行适用的安全观察。不盲目向用户生产数据重放新增、删除、发送等测试操作。正式入口不可用时不能报告完整交付，已提交的安装事实仍需保留并明确展示。

Preview 使用临时 DataRoot，更新验证使用生产数据副本，测试数据不进入正式实例。UI 明确区分预览与已保存的运行入口；用户需要保留预览输入时，应明确执行受支持的数据保存动作，不暗中复制测试数据。

### 成功结算

~~~text
当前版本的所有适用必需验证通过
且安装提交成功
且插件库可读取该版本
且需求所要求的正式入口可用
且交付回执持久化
~~~

包结构 Ready、源码生成、ZIP 存在或模型回复“已完成”都不能代替上述条件。现有输出交付应增加类型明确的 Plugin 引用，不从自然语言关键词推断完成。

需要外部账号、配置、授权或本机代码信任时，任务显示等待输入，补齐后自动继续。一键定义为一次提交由系统完成闭环，可以多轮实现和修复；不承诺任意模型一次回答就能实现任意需求。

### 本机代码与外部效果

沿用现有信任模型：UI 受 CSP 与 Bridge 控制，Service 是用户授权运行的可信本机 JS，独立 Node 进程与临时 DataRoot 不等于系统沙箱。

Service 首次执行包括 activate 检查，必须具有适用的信任授权。复用已经覆盖当前任务与权限的授权，超出授权范围时再请求补充；授权范围、版本及有效期遵守真实合同，不能以“开启开发模块”替代所有本机代码和外部效果的许可。

测试外部写入时使用明确允许的测试端点或效果授权。仅隔离插件数据不能证明外部系统没有被修改。用户输入 Credential 时复用既有安全配置入口，Agent 只取得适用引用。

## 9 状态展示与故障恢复

执行、重试、预算、取消和恢复继续归普通会话 Runtime 与现有 Agent 执行日志管理。创作阶段是这些事实的投影，Draft 只保留源码与版本事实，不再拥有模型 worker 或独立 Generating 主状态。

会话显示整理需求、生成、构建、验证、修复、安装和交付阶段，以及真实当前动作和失败原因。模型回合终止与创作请求结算分别呈现，不按文件或消息数量计算虚假完成百分比。

| 情况 | 行为 |
| --- | --- |
| 模型或协议失败 | 记录实际原因，复用该 Agent 的既有重试与故障转移 |
| 包、语法或 SDK 错误 | 给出文件、字段与支持合同诊断，进入同一 Agent 的修复循环 |
| 业务验收失败 | 保留原验收条件与观察，修复后重新验证 |
| 配置或授权缺失 | 会话显示具体输入项，保留草稿，完成后继续 |
| 插件被其他入口更新 | CAS 拒绝覆盖，重新读取并明确处理基线差异 |
| 用户停止 | 取消模型、构建及验证，关闭临时资源，阻止尚未提交的后续安装 |
| 停止时安装已提交 | 保留已安装成果，显示已提交事实，不自动删除插件 |
| 应用崩溃或重启 | 根据现有执行日志和安装 mutation 记录恢复确定结果，未知外部效果不盲目重放 |
| 安装成功但回执丢失 | 查询已提交结果，补发交付回执，避免重复安装 |
| 页面切换或断线 | 通过会话事件与后台事实重连，执行不依赖独立页面轮询 |
| 自动修复预算用尽 | 保存失败项、诊断和源码，允许原会话继续，不标成功 |

为一次任务设置自动修复次数、模型执行预算和总耗时上限，使用现有预算机制；可先采用不超过三轮自动修复作为首期默认值，并通过真实验收调整。用户停止或预算耗尽后，不在后台继续消耗模型。

打开草稿、文件写入、创建首消息与安装分别使用稳定幂等依据。重复点击、响应丢失和恢复只能返回或继续原结果，不能生成重复实例。

安装提交点必须有可恢复的持久记录，关联操作键、owner、目标插件和准确 Artifact。恢复时先查询已提交结果，再补齐交付检查和成果回执；不能因为最后一个 HTTP 响应或会话事件丢失就再次创建插件。用户停止与安装提交竞争时，以真实提交事实为准，提交前取消阻止安装，提交后保留成果。

错误信息应包括稳定错误码、阶段、具体原因、是否可重试和解决动作。脱敏日志用于诊断，用户界面提供能理解的反馈。

## 10 会话与插件库的界面职责

| 界面 | 职责 |
| --- | --- |
| 会话 | 输入需求、生成与修改、显示工具轨迹、阶段、配置等待和成果卡片 |
| Agent 工作台 | 开启整个插件开发模块、保存必要操作权限、修复模型或依赖 |
| 插件库 | 创建快捷跳转、导入、查看、启停、配置、导出、恢复和删除成果 |
| 插件运行页 | 打开小程序或使用现有插件详情与试调用入口 |
| 会话 Workspace | 按通用成果适配器展示预览、文件与验证详情 |

成果卡片显示“已验证并保存”或具体未完成状态，提供打开、试用和继续修改。它从后端读取 plugin_id、准确 Artifact、实例形态、验证结果和运行入口，不根据模型描述制造状态。

未完成草稿在插件库提供“继续会话”；已有插件修改后仍是同一个实例与数据所有者，不产生另一套发布对象。

在 880×600 下采用桌面面板切换或折叠，较宽布局可并排显示会话与预览。窄 Pane 使用容器查询，不引入手机抽屉、触摸分支或低于 880px 的布局合同。

## 11 数据与接口职责

| 事实 | 权威 owner |
| --- | --- |
| 默认 Agent 与模块授权 | 现有工作台配置、稳定预设和 Compiler |
| 创建意图 | 现有会话草稿，记录需求、附件与目标插件版本 |
| 用户与助手消息 | 普通 Conversation 与会话日志 |
| 执行、阶段与恢复 | 现有 Runtime、工具调用及 Agent 执行事实 |
| 源码 | Draft 工作目录、revision、来源会话与基线插件版本 |
| 运行产物 | 现有不可变 Artifact |
| 验收与交付 | 现有执行回执和通用成果记录的 Plugin 扩展 |
| 安装、实例与数据 | Plugin Repository、Install Service、DataRoot 与 Runtime |
| 插件扩展点 | 现有 Action 与 Binding 注册、启停和版本检查 |

一个会话可以生成多个插件，Draft 与 Conversation 通过来源引用关联，不合并身份。删除创作会话不自动删除已安装插件，删除插件也不篡改历史完成证据；卡片显示当前插件是否仍存在。

最低数据关系为：创建意图关联默认或当前 Agent；会话请求关联需求及必需成果；Draft 关联 owner、来源会话与消息、修改基线和 revision；验证记录关联准确 Artifact 与执行上下文；交付回执关联真实安装结果。执行阶段由现有 Runtime 事实投影，Draft 不维护第二套聊天或模型执行状态。

新增普通会话启动 preflight，返回 ready、需配置模块或不可用的结构化结果。它不创建模型任务或草稿。实际创建、发送和停止继续走既有 Conversation 接口和执行服务，启动时重新检查模块与稳定版本。

Plugin Router 保留用户 Core 操作适配器，移除模型服务、Prompt、生成 worker 与生成取消 API。Agent 工具通过同一应用服务调用领域操作，不让模型拼接内部 HTTP 地址。

外部导入与 Agent 生成共用 Stage、Validate、Activate；通用安装器仍负责结构与启动检查，不自动执行带效果的业务测试。业务验收属于明确的创作任务。

## 13 数据与旧入口迁移

1. 保留 plugin_id、当前及 previous Artifact、DataRoot、配置、grants、Credential 引用、收藏、启停及回收状态。
2. 保留有效草稿源码与 base revision，建立普通会话来源关联；懒创建关联必须幂等。
3. 已保存的 Draft messages 转为普通会话可展示的历史记录，明确标记导入来源，保留内容与可确认的原始时间。继续任务通过正常会话准入关联有效 Agent；历史导入不能伪造执行快照、工具结果或成功回执。原消息没有时间或执行证据时如实标记缺失，核验迁移后删除旧平行聊天合同。
4. 旧 Generating 状态在升级时结算为中断，保留一致文件和继续入口，不复活旧模型 worker。
5. 已丢失、从未持久化的失败需求如实说明，不能根据草稿伪造历史消息。
6. 更新内部书签、编辑入口和成果引用；旧 Creator 路由退出生产执行，不保留可运行兼容 Creator。
7. 迁移结果核验后停止旧状态读写，不保留长期双写或两套运行数据。
8. 中断的安装继续通过原 mutation 记录恢复，不能因 UI 重构重复安装或清空数据。

迁移执行前保存可恢复备份，迁移步骤使用稳定映射与事务或可恢复进度，重复运行不产生重复历史与实例。以实例数量、关键 ID、业务数据和可继续草稿核验结果；核验完成前保留可恢复原记录，完成后停止旧合同的读写。

实现与旧链路删除在同一发布版本切换。破坏性重构针对代码与合同，不自动授权清空用户数据；若需要丢弃实验数据，另行明确范围。

## 14 实施顺序与阶段门禁

| 阶段 | 工作 | 完成条件 |
| --- | --- | --- |
| 0 | 真实失败基线 | 保存代表性失败需求、日志与模型信息，明确已有问题，后续能够对照 |
| 1 | 固化合同 | 模块级检测、工具、草稿关系、验证与成功条件确定，修订边界规格 |
| 2 | 模块与最小闭环 | 默认通用 Agent 开启模块后，真实需求生成并安装持久待办小程序 |
| 3 | 统一入口与往返 | 默认解析、未开启引导、保存继续、需求保留、幂等启动全部通过 |
| 4 | 完整生成与验证 | 能力插件和混合插件可生成、试运行、修复并证明可用 |
| 5 | 成果与恢复 | 普通会话交付卡片、实例更新、数据保护、取消和恢复通过 |
| 6 | 迁移并物理删除 | 用户数据保留，旧 Creator、生成接口、平行聊天和 worker 退出 |
| 7 | 真实模型发布验收 | 代表性需求集重复运行通过，只有统一新链路 |

先验证真实默认 Agent 能完成闭环，再扩展界面和管理操作。阶段可以形成顺序提交，但发布时不长期并存两套创作系统。

## 15 验收合同

| 类别 | 必须通过 |
| --- | --- |
| 模块级检测 | 尚未创建任何插件时即可检测整个模块；不要求选择某个插件或目标 Agent |
| 默认 Agent | 新建任务使用配置的默认 Agent、稳定版本和模型路由 |
| 已有会话 | 继续使用当前 Agent，保留需求与上下文，不默默换成全局默认 |
| 未开启 | 进入工作台，不提前创建插件、草稿或模型任务 |
| 操作授权 | 开关已开但缺少写入或安装操作时给出具体修复项 |
| 工作台往返 | 需求和附件在保存、刷新与返回后保留，只接受一次请求 |
| 小程序 | 真实需求生成待办，添加、完成、重建 Surface 后保留数据，保存后实际打开 |
| 能力插件 | 真实需求生成文本处理等 Action，无 UI 也可验收，正式声明的消费入口实际调用成功 |
| 混合插件 | 实际 UI 使用 Service Action，共享同一实例与持久数据 |
| 更新 | 保留用户业务数据，迁移失败保持原版本可用 |
| 自动修复 | schema、SDK、语法或业务失败能得到诊断并在同一 Agent 修复，新版本重新验证 |
| 完成防伪 | 仅文本“完成”、文件存在、结构 Ready 或安装提交都不能提前报总成功 |
| 多个成果 | 一个请求要求多个插件时全部分别验收；更新旧插件不得用其已有 plugin_id 提前结算 |
| 验收完整性 | 超时、取消和修复不删除必需用例；数据持久化要求有重建后观察证据 |
| 输入等待 | 配置、Credential 或适用信任缺失时显示等待，补齐后继续 |
| 插拔与独立运行 | 关闭模块后新任务无创作工具；已有插件及数据仍可由 Core 运行和管理 |
| 取消与恢复 | 无延迟安装，重复请求无重复实例，安装提交与回执丢失可以正确恢复 |
| 数据隔离 | 多用户、多插件和多草稿按 owner 隔离；Preview 不污染生产数据 |
| 原应用重启 | 发布验收覆盖完整退出启动后的插件与业务数据恢复 |
| 桌面边界 | 880×600 下可完成适用流程；WebUI 不越过既有只读权限 |
| 旧链路退出 | 没有独立 Creator、整包模型生成接口或 Draft 聊天 worker |

生成验收必须使用产品声明支持的真实 provider 与模型，分别重复验证 UI-only、headless、mixed 和更新。保存原需求、模型版本、运行证据、修复次数和失败阶段；wiremock、固定源码或人工导入不能替代真实生成验收。

跟踪请求到成功交付的成功率、首轮实现正确率、自动修复成功率、耗时和失败原因。固定验收需求集的必需项全部通过；没有实测基线前不宣称已有成功率，未完成交付的实例不计为生成成功。

后续代码实施按范围运行会话与工作台交互测试、Module 授权与合同测试、插件 SDK 与存储安装测试、真实绑定及生成验收。renderer 或 UI 规则变化后运行 bun run check:desktop-ui-boundary，并执行直接相关的 Unified Plugin、合同生成和 i18n 检查。

本次整理的验证范围是文档内容、结构与源码引用，不运行构建、UI 验收或真实模型生成。实现记录中的检查结果保持独立，不能替代上述发布验收。
