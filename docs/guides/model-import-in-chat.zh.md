# 在会话中录入模型

用户可以在通用 Agent 会话里提供服务地址、模型 ID、用途以及必要的认证配置，让 NomiFun 把模型保存到模型管理。也可以在模型管理页点击“在会话中添加 · 通用 Agent”，进入一个预填了录入要求的会话草稿，补全后再发送。

例如：

> 请给已有的“公司模型网关”添加一个对话模型，模型 ID 是 example-chat，使用 OpenAI Chat Completions 协议。沿用现有地址和密钥，不切换默认模型。

> 请添加这个新提供商：名称是“测试服务”，API 根地址为 https://models.example/v1，模型 ID 是 example-image，用途是图片生成，兼容 OpenAI Images 接口。认证配置如下……

需要先有一个可以正常对话、调用工具的模型来完成录入。聊天中粘贴的内容会交给当前会话模型处理，并遵循普通会话历史的保存规则；不想把密钥放进会话时，可以先在模型管理页录入提供商和密钥，再让 Agent 使用已有提供商添加模型。

## 调研结论与接入方式

现有模型管理已经通过 `ProviderService`、`ProviderModelService` 和 `ProviderConnectionService` 管理提供商、模型能力和连接。协议枚举、端点规则与认证要求由 `nomifun-model-invoke` 的 manifest 统一提供。缺失部分是 Agent 可发现、可授权、可调用的配置入口。

本次增加 `model.management` 模块，注册到现有 Kernel 和工具 Schema Router，并加入官方通用 Agent 的明确 Action 授权：

| Action | 行为 |
| --- | --- |
| `model.management/inspect` | 查询已有提供商、模型、连接角色，或者查询指定平台与用途的协议清单。不会向 Agent 返回已保存的密钥。 |
| `model.management/create_provider` | 复用管理页的创建流程，保存新提供商、第一个模型及其命名连接。 |
| `model.management/add_model` | 向已有提供商添加模型，使用已有连接，不替换已有模型的能力配置。 |

Agent 先检查已有配置和协议，使用用户提供的信息与协议清单中的默认值补齐录入请求。缺少模型 ID、地址或凭据时需要追问，不能编造。模型能力仍按 `(provider_id, model, task)` 保存，没有新增平行配置表、数据库迁移或直写 SQLite 的工具。

成功写入后，宿主发送仅面向配置所有者的 `providers.changed` 事件，刷新模型管理及模型选择器共用的缓存。工具输出只包含保存结果、标识和凭据是否存在；错误会按本次提供的凭据进行脱敏。

会话校验也做了必要调整：新建 Chat 路由的配置摘要只包含所选模型的能力、提供商认证及连接配置。给同一提供商新增其他模型不会中断当前对话；修改当前模型的端点、能力或提供商密钥仍会使旧路由失效。旧版本保存的整个提供商摘要继续按原规则严格校验，没有放宽旧快照的权限。

## 行为边界

- 新提供商的初始能力和命名连接由原服务校验后一起保存；不支持的协议、错误认证形态和缺失连接会报错。
- 重复提供商（同名同地址）或已有模型会返回冲突。新增模型复用配置版本检查，避免并发写入覆盖已有能力。
- 一个 Action 录入一个模型；多个模型可以连续调用。跨多个 Action 的批量录入不是一个事务，Agent 应据实说明每个模型的成功或失败。
- 此入口不删除配置，不更新已有凭据，不设置全局默认模型，也不更换当前会话模型。
- 保存结果明确标记 `connection_tested: false`。录入成功只证明配置保存通过校验，服务可达性、密钥权限和实际推理能力仍以模型管理中的检测为准。
- 只有获得对应 Action 授权、且由本机配置所有者运行的 Agent 能调用。旧会话继续使用原来的授权快照；从本入口新建会话会采用当前通用 Agent 模板。已有个人 Agent 可在工作台启用“模型管理”模块后开启新会话。

## 验证

业务测试使用隔离数据库检查保存与管理页一致、凭据加密、重复录入保护、无效输入无半成品、命名连接及多模态配置、并发新增和错误脱敏。产品链路测试使用脚本化模型服务，通过真实 AgentSession、工具计划、Kernel 和管理 API 完成录入，并覆盖向当前提供商新增模型后的后续回复。脚本化服务不代表真实供应商或自然语言理解的线上验收。
