# Agent 工具契约与恢复循环复查

本报告接续 [macOS 首轮排查](2026-09-26-macos-agent-reliability.zh.md)。本轮针对工具契约、恢复分类、证据失效和终止条件复查，保留全部中间失败样本。

## 两个原会话实际发生了什么

两个会话都使用「通用」Session-only preset，运行 build digest 为 `29a38882d485bcdd88692544c9d52fecc1acda0537bfb9e099edacd11526356b`。这证明已加载上一轮修复，不能继续把现象归因于旧二进制。

| 原会话 | 原始任务 | 原模型 | 主模型步骤 | 模型工具结果 / 错误 | 内部规则读取 | 其他开销 |
| --- | --- | --- | ---: | ---: | ---: | --- |
| `01a0dc0b-222f-7462-b799-ffeb7f30c323` | 帮我实现一个h5五子棋游戏 | agnes-2.5-flash | 15 | 14 / 5 | 18 | 1 次输出截断 |
| `01a0dc1d-07b4-7b00-93a7-d22b075a0316` | 帮我实现一个h5贪吃蛇游戏 | step-3.7-flash | 35 | 38 / 8 | 74 | 2 次协议拒绝；7 次摘要调用、6 次上下文替换 |

两者最终都记录为 completed，但完成过程并不可靠。五子棋记录的主模型 input/output usage 为 208,494 / 10,397；贪吃蛇为 401,193 / 25,479。这些值不含摘要调用，也不包括提前中断后未收到的 usage，不能作为完整账单。内部规则读取另列，不能用这些大量成功的内部调用稀释模型工具错误。

五子棋：读取片段时缺少历史 SHA 被拒绝；同时提交计划和完成报告被整批拒绝；随后因为计划缺失、旧调用 ID 的 workspace epoch 不匹配，继续补内部表单。最终接受的证据是 `wc -l`，它只能证明该命令的观察，不能证明游戏功能。

贪吃蛇：计划标签稍作改写但没有 explanation 就被拒绝；三个文件被重复整体写入；一次 `node --check game.js` 正常完成后，后续错误地把完整命令放进 executable 字段。程序没有启动，却使已有观察失效并隐藏命令工具。最后又连续因需求 ID 重复、旧证据 ID、步骤名称不完全一致而拒绝完成报告。

## 全局设计问题与改造

### 1. 将规划文字与执行权限分开

规划是模型的工作记录，不应成为每次工具使用必须重新填写的表单。初次、状态更新和计划修订都可以省略 explanation；不可丢失的用户要求仍由引擎保留。恢复需要显式重新规划、补丁再观察、权限验证等条件继续有效，说明文字本身不是这些条件成立的证明。

流程暂时阻塞不再从冻结工具表删除功能。工具可用性和当前是否允许继续执行是不同事实，否则模型会把一次参数错误理解成「Shell 权限被撤销」。

### 2. 用一次交付报告关闭任务

`report_completion` 可以在验证完整报告后关闭可选计划，无需先逐项改状态再另行提交。也支持顺序为 `update_plan`、`report_completion` 的纯控制批次。混入实际执行调用仍不允许；计划失败时，依赖它的报告不会应用。

有效报告通过原子用户输入屏障后，直接发布 summary 和未验证/受阻披露，不再请求模型撰写一次结束语。用户在结束屏障前追加指令时，旧报告失效并继续处理；未结束进程、待重新读取的失败补丁和受阻条目仍不能作为成功交付。新增独立 `completion_delivered` 事件区分引擎发布与模型输出，保证持久化、界面文本、历史回放顺序一致。

完成条目描述交付项和检查，不必逐字复刻计划标签，也可省略显示标签。同一用户要求可以对应多个实现条目；省略 requirement_ids 时覆盖保留的要求，显式填写仍不能丢失要求。范围变更继续需要较晚用户输入的准确引用，同一个要求不能同时声称按原范围完成又被改范围。

新增 `evidence_paths`，由引擎将精确工作区路径解析到当前可用的成功观察。原有调用 ID 方式保留。路径不存在、观察失败/过期、进程仍在运行或恢复条件未满足时，不能将报告当作成功，也不会在校验失败后关闭计划。

### 3. 证据按已知文件作用范围失效

写入 CSS 不应自动抹去刚写好的 HTML 的观察。对于已知、受文件 owner 限定的互不相交写入，保留未受影响的文件证据；同一路径及删除目录下的证据失效。命令、VCS、外部资源请求和未知作用范围仍采用保守的全局失效。

带有可写 before_tool 插件的包装调用不使用局部作用范围优化；ASCII 路径按大小写可能相同保守比较，非 ASCII 路径不跨文件修改复用，防止 macOS/Windows 卷的路径别名破坏证据有效性。

历史观察保留原始 epoch，没有把旧事件重新标成新读取。模型上下文只列出当前可用证据及对应文件，不让模型自己搬运和比较底层 epoch。它仍是执行观察，不是文件锁、外部并发修改检测或独立语义验收。

### 4. 区分没有启动与启动后的失败

进程 owner 分别保留「没有活动进程」和更强的「请求的程序从未启动」事实。启动前参数/路径准备失败、明确 spawn failure、容量预留失败可证明后者；启动后丢失但已清理的进程不能证明没有执行过。

已证明未启动的调用返回有界 `not_started` 观察，保持失败状态，但不使早先文件和检查证据失效，也不要求凭空重新规划。真正执行过的失败命令、不确定结果、未清理进程仍遵循原有恢复与证据约束。

### 5. 工具接口符合常见操作习惯

- `exec_command` / `start_process` 新增明确的 `cmd` 脚本入口；`command + args` 保留为字面程序调用。两种形式不能混用，不根据字符串内容猜测或拆分参数。脚本交给共享进程运行时的 Posix/PowerShell 实现，保留 Windows 的退出状态和清理逻辑。
- `read_file` 支持 `start_line` / `line_count`。普通 byte offset 读取是独立的当前版本观察，不再隐藏地要求历史哈希；每次仍返回完整源 SHA。显式 `expected_sha256` 仍严格检查，内部 AGENTS 分页读取继续逐页带版本校验。
- 读取格式接受无作用的显式默认值 `recursive=false` / `missing_ok=false`；仍拒绝与格式不兼容的 true 值或有作用参数。控制工具同样经过 schema 预检，错误返回 `/criteria/*/rationale` 等 schema 路径，避免模型把嵌套字段不断补到根对象。反馈不回显私有参数值或任意字段名。
- `git_status` 对真实的无仓库目录返回 `is_repository=false`，不初始化 Git。损坏的 Git 元数据、权限/目录问题继续返回错误。
- 文件写入回执包含 bytes、line_count、sha256，避免仅为计算行数和获取指纹再启动命令。这些不是游戏或测试成功的证明。

### 6. 正确计算上下文开销

旧校准将上轮 input + output tokens 对比上轮输入估算；下一轮又计算新增输出消息，导致输出被重复计入。现在只使用实际 input tokens 校准下一轮输入，并保留字节估算的保守余量。输出预留、上下文硬上限和真正 prompt-too-long 的恢复仍保留。

### 7. 先读取终止原因，再判断错误类别

原 API 探针捕获了 `finish_reason=length`、正文含工具调用标记、无原生调用的返回。原运行时看到标记便中断，因而无法读取 length，误入协议纠正；要求再次输出同一大函数仍可能反复触顶。

现在先屏蔽可疑正文，再在已有流限制和取消控制下读取终止原因。length 走输出大小恢复，整批提议不执行，明确要求分块完成全部原任务；涉及文件/命令的分段生成会启动完成核验，不能把初始结构直接作为完成交付。完整响应中的真正格式错误仍走原有有界协议纠正。

协议纠正可从短函数名提示中选择当前已暴露的精确函数，并仅为该次纠正缩小展示；不会读取或执行文本中的参数，也不授予能力或重置重试预算。新用户输入会释放这个展示约束。存在已丢弃原生前缀的混合响应不会据此跳过先前操作。

## 仍然存在的开销与结论边界

当前样本证明已确认的终止、参数恢复和证据规则可以正常工作，但**不能宣称整体速度已经达到稳定交付标准**。也不声称 99% SLO：样本少、模型有随机性，且中间样本使用不同构建。

最终贪吃蛇的 1 次参数错误是同时填写 `cmd` 和非空 `args`，预检阻止执行并在下一步纠正，没有触发无谓重新规划。最终五子棋的 3 次拒绝分别为命令之后引用过期文件观察、编造需求 ID、显式空 ID 列表漏掉保留要求；最终修正为真实 `input_0` 后直接结束。后三项不能通过允许过期证据或丢弃用户要求来换取成功率。

剩余耗时主要表现为生成触及输出预算、上下文压缩后的重复读取/目录检查，以及模型逐项更新计划。原配置没有提供模型上下文/输出上限，运行时采用 32,768 / 4,096 的保守回退；本轮没有凭猜测放大这些值。后续性能优化应优先基于明确的模型能力配置和压缩前后任务状态保留做测量，减少恢复后的重复检查，并使需求引用反馈更直接。它们与本轮已经修复的“有效报告后任务重开”应分开评估。

无需修改原会话或迁移用户数据。本轮改变涉及运行时和工具契约，使用当前构建新开会话进行验收；旧会话的冻结工具快照不会被追溯改写。
